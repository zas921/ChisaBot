## O-01：Android 同步和并发边界

### 发现

1. `startSync` 每 3 秒查看 `running`，本机空闲时只有服务器正在运行才开始读取历史。另一端在两次轮询间完成短回合，手机可能一直看不到新消息。见 [AppViewModel.kt:457](../android/app/src/main/java/cn/ayase/chisabot/AppViewModel.kt#L457)。
2. `loadChat` 的旧请求未取消，返回后直接设置全局线程和消息。慢网下先打开 A 再打开 B，A 的迟到响应可能覆盖 B。见 [AppViewModel.kt:388](../android/app/src/main/java/cn/ayase/chisabot/AppViewModel.kt#L388)。
3. 续期请求开始前先设置 `lastRenewAt`，60 秒内其他请求直接返回失败；多个接口同时遇到 401 时，可能一个正在成功续期，另一个已经触发退出。见 [AppViewModel.kt:125](../android/app/src/main/java/cn/ayase/chisabot/AppViewModel.kt#L125)、[Api.kt:101](../android/app/src/main/java/cn/ayase/chisabot/net/Api.kt#L101)。
4. 首次选多个附件会并发执行 `ensureChannel`；缺少进行中请求复用，可能分别创建频道，使附件分属不同会话。见 [AppViewModel.kt:487](../android/app/src/main/java/cn/ayase/chisabot/AppViewModel.kt#L487) 和第 719 行。

### 方案

- 复用 Web 已使用的会话 `seq/revision` 同步接口，消息变化与忙闲状态分别处理。序号有变化即补消息，编辑/重生成导致版本变化则重建显示。
- 聊天状态引入服务器地址、机器人、线程和加载代次；切换时取消旧加载，响应落地前再核对代次。
- 为续期和首次建频道各维护一个共享的进行中任务；并发请求等待同一结果。
- 为 ViewModel 注入 API、时钟和协程调度器，让这些时序能在自动化测试中稳定重现。

### 验收

- 用假 API 与虚拟时钟固定时序：首次轮询空闲后，另一端在随后 500ms 内开始并结束；下一次轮询仍为空闲但 seq 已变，手机应补齐完整消息且无重复。覆盖同步基线建立前后、后台期间完成及编辑重发；回前台立即同步由 O-05 承接。
- 人为让 A 的响应晚于 B：B 的线程、消息、忙闲、错误均不被 A 覆盖；切服务器、退出登录同样成立。
- 10 个并发 401 进入后再释放续期成功响应：只发起一次续期，原请求各重试成功且不退出；设备令牌撤销时只触发一次退出流程。
- 首次选择 8 个小型测试附件，让创建响应延迟以制造并发：只建一次频道，全部上传使用同一频道；切换机器人后旧上传不覆盖新状态。允许已经发出的旧请求完成，但结果不能污染当前会话。
- 最后进行 PC ↔ Android 真机对测：短回复、长工具、切网、锁屏、停止和重生成。

## O-02：先保证恢复一致，再减少对话写放大

### 发现

- `connect` 先读消息快照，再另查最大事件序号，最后丢弃不大于该序号的缓冲事件。两次读取间有新事件时，序号可能已经前进，而快照尚未包含它，存在重接漏增量的窗口。见 [local-conversations.ts:1421](../server/src/local-conversations.ts#L1421) 及第 1451 行。
- 每个事件单独写数据库；每次消息变化又深拷贝历史、投影并写入完整 JSONB。长历史叠加密集文本/工具参数增量，会放大 CPU、序列化和数据库写入成本。见 [local-conversations.ts:941](../server/src/local-conversations.ts#L941)、[capture:1006](../server/src/local-conversations.ts#L1006)、[snapshot:316](../server/src/local-conversations.ts#L316)。
- 现有“工具等待改为静默超时”处理了排队导致的误失败，但没有消除这些逐事件处理成本。

### 方案

第一步单独修一致性：为消息/状态快照记录它真正覆盖到的 `snapshot_sequence`，同一次提交保存，一致读取；连接从该检查点补齐后续持久事件，并与实时事件按序去重。补齐过程要有明确上界和分批策略。

第二步再做性能：基准确认后合并高频快照更新，先从 100–250ms 的候选窗口试验；减少队列里重复保留的全量副本。事件批写只能在测量证明值得做后实施。

### 约束与验收

- 不能直接给当前 `capture` 加 debounce：这会扩大快照与序号不一致的窗口。
- 工具调用/结果、审批挂起、停止、错误、正常结束和释放锁之前必须完成相应持久化。
- 保留先持久化再确认事件的语义；批写如采用，需验证序号、顺序、错误传播和崩溃后的恢复。
- 用可控事件顺序覆盖“读取快照途中收到新事件”，重接后既不漏字，也不重复工具调用。
- 以 100/500/2,000 条历史和大段工具参数为固定样本，测首字延迟、工具事件等待、每轮快照次数/字节量、数据库写入时间和峰值内存。
- 通过停止、重启、断网恢复、编辑重发、审批续跑和队列持久化回归；性能改善以同机前后数据说明，不预先承诺百分比。

## O-04：发布来源与快速更新完整性

### 发现 A：手工发版没有绑定标签对应的源码

输入 tag 只与版本字符串比较，checkout 没指定该标签的 ref；发布使用 `github.sha`，并允许覆盖现有资产。当主分支和标签不同、版本字符串又相同时，可能把新代码打的包放到旧标签下。

证据：[release.yml:58](../.github/workflows/release.yml#L58)、第 70、366、381 行。

方案：先解析确定的发布 SHA，让所有测试和构建任务 checkout 同一 SHA；产物清单记录提交、锁文件摘要、版本和文件哈希。相同资产可幂等重传，哈希不同的同名资产不能静默覆盖。

发布前还需处理本地 PC `0.1.56` 与 Android `0.1.57` 的差异：当前工作流要求两端版本相同，会主动阻止该状态出包。本轮只记录此约束；后续发版按[发布流程](release.md)准备版本一致的提交。

验收：主分支与旧标签不同、版本字符串相同的场景，要么明确构建标签源码，要么在构建前拒绝；各产物都可追溯到同一提交。保留工作区已增加的 Android 签名与包信息校验。

### 发现 B：快速更新遗漏部分镜像输入

完整镜像包含 `deploy/migrate-wait.sh` 和 `scripts/composio-smoke.ts`，但这两项既不在依赖指纹里，也不在快速替换上下文里。只改这些文件时，版本号可能变新，容器中的脚本仍旧。

证据：[Dockerfile:320](../Dockerfile#L320)、第 175 行；[deps-fingerprint.sh:8](../deploy/updater/deps-fingerprint.sh#L8)、[update.sh:261](../deploy/updater/update.sh#L261)。

方案：先把遗漏项加入必须完整构建的输入；再统一维护快速替换与完整构建清单，对 Dockerfile 运行时 COPY 输入做覆盖检查。

验收：单独修改任一遗漏文件都必须触发完整构建；在隔离构建中核对关键启动文件哈希；每类运行时输入都有明确更新路径。

## O-05：Android 旁观改为增量同步

当前 `watch` 每 1.5 秒下载完整历史并读取 inbox，另外 3 秒同步也读 inbox；忽略响应耗时，仅这两路理论上限约 100 次 HTTP/分钟，未含确认卡等请求，也不是实测数据。历史越长，重复下载与解析成本越大；循环也未绑定 Activity 前后台生命周期。

证据：[AppViewModel.kt:418](../android/app/src/main/java/cn/ayase/chisabot/AppViewModel.kt#L418)、[startSync:457](../android/app/src/main/java/cn/ayase/chisabot/AppViewModel.kt#L457)。

先利用 O-01 的变化戳避免无变化全量下载，再接增量流；前台恢复立即补齐，后台暂停旁观轮询。使用 500/2,000 条历史各旁观 10 分钟，记录请求数、字节量和主线程耗时；后台不再高频取历史，前台网络正常时以 3 秒内追齐为目标。

## O-06：事件保留与存储维护

`openbot_local_events` 持续追加，常规保留没有归档/压缩期限；当前主要在删除线程和截断时删除。长时间使用后的数据库和备份成本会继续增长，但本次没有测生产体积。

证据：[local-conversations.ts:1587](../server/src/local-conversations.ts#L1587)、[thread-truncate.ts:113](../server/src/thread-truncate.ts#L113)。

先增加按事件类型/会话统计的只读报告，再设计保留策略。保留消息快照、运行边界、工具/审批终态和必要索引，压缩较早的高频增量；先提供 dry-run，显示预计影响的行数和空间。

不能直接按日期删除整个事件段：重生成目前依赖 RUN_STARTED 的序号与消息 ID，其他路径还读取运行终态、用量和审批事件。清理前必须完成检查点设计及兼容读取。

验收包括备份恢复、清理前后历史一致、旧消息重生成、审批恢复、跨端同步；正在运行/等待的回合不进入清理集合。实际释放空间与数据库维护开销需在隔离数据副本中测量。

## O-07：补齐可衡量的运行指标

现有健康接口和 SEND/STREAM/SSRF 计数可以保留。近期新增的 `tool-failed`、`output-limit-rejected`、`frontend-relay-stale` 主要是日志，尚未进入现有预算统计；也缺少快照写入与接力耗时这类本轮优化需要的指标。

证据：[ops-counters.ts:12](../shared/ops-counters.ts#L12)、[copilot.ts:711](../server/src/copilot.ts#L711)、[local-conversations.ts:772](../server/src/local-conversations.ts#L772)。

扩展现有轻量指标：每轮首字/结束耗时、工具等待与失败原因分类、快照次数/字节量、重接次数、接力超时和事件表体积。使用固定分类，避免把线程 ID、工具参数或聊天正文作为指标标签。

验收：一次模拟工具失败或接力超时能从健康视图定位；优化前后的同一负载可直接比较；保留日志与现有指标的轻量实现。

## O-08：工作流并行预算漏计

两个并行步骤都先读取同一个 `state.tokens` 作为 base，结束时各自写 `base + used`，后完成的步骤覆盖先完成的计数。

证据：[workflows/engine.ts:441](../server/src/workflows/engine.ts#L441)、第 462、551 行。

本次用纯内存 store 与假模型回合复现：预算 2,000，两个并行步骤各估算 1,281，步骤合计 2,562，最终总计却是 1,281，并标记成功。这里是程序内部估算 token，不是供应商真实计费结果。

建议汇总已完成回合与各在途回合的用量，形成共享预算判断；错误、取消和格式修正不能漏记。验收覆盖并行超额、不超额、多次修正与取消。工作流入口默认隐藏，若当前主要使用普通聊天，可排在核心同步修复之后。
